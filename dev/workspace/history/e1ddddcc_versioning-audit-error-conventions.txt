[ASSISTANT 💬]
Strong threads — stronger than I expected. The spec already *demonstrates* your convention three times and never *states* it once.

## The load-bearing find: `steps.md:127-133`

The Dispositions catalogue lists three error classes. All three end the run:

- **Half-applied** — "Report the error to the user, exit the skill, advise manual fixing, and suggest an issue... Never re-run the step over its own partial work."
- **Failed permissions** — "Report what was denied and what it was needed for, then stop... suggest an issue... Never route around a denial."
- **Insufficient references** — "Report the gap and exit... suggest an issue... Never invent the missing content."

Three classes, one identical shape: **report → advise manual repair → exit → suggest an issue**. The section header even says "**Hard exit and repair** is the default posture" — then scopes it to "destructive errors", which is the mis-statement. Nothing about a missing reference is destructive, and it still hard-exits.

So the spec has your law empirically and states it nowhere. Worse, it's a single-source-of-truth breach *inside the spec* — one fact, three homes, which is why each entry re-states "suggest an issue to inform the skill repair agent" three times. The catalogue should be a law plus a thin per-class list of *what to report*, not three near-duplicate dispositions.

## Supporting threads

- **The preamble already says it.** "A step that cannot be completed falls to the error drain step" — verbatim in every DraftHorse document. Every resume branch in the wild is a document not trusting its own preamble. `+Execute` wrote 13 lines and a bash block to re-implement a line it already carries at `:86`.
- **`conventions.md:10`** — "coverage is subtractive, not enumerative". A resume path *is* enumerative error handling. The drain exists precisely so steps don't do it; your convention is just applying that consistently instead of stopping at half-applied.
- **Dormant steps** (`conventions.md:6`, `steps.md:153`) — unfired branches cost nothing, so there's no pressure to make steps multi-purpose across failure states.
- **`steps.md:108`** — a bail is already a sanctioned *Suggested next actions* use, first-class.
- **`conventions.md:22`** — Dynamic Improvement is the tail of your convention: bail, advise, and file the issue so the gap gets fixed upstream rather than patched per-skill.

## The one line the convention must not cross

`steps.md:116`: "Approval is state, and it is revocable: revising an approved artifact un-approves it and everything downstream of it, so **the owning step's start condition holds again**."

That's the spec's only sanctioned re-entry, and the mechanism matters — not a recovery branch, just a condition that became true again. Same for loops (`steps.md:151`: "a loop is not a special structure — it is a start condition that holds again").

So the distinction to write in:

- **Re-holding** — the world changed, the condition is true again, the step carries *nothing* about its own history. Legal, and it's how loops and gate revisions work.
- **Resuming** — the step knows it failed before and behaves differently because of it. Banned.

`+Preflight`'s "or a precondition failed and has since been repaired" fails this test: the repair clause is the step remembering. Strip it and the *plain* condition "preconditions not verified this run" already re-holds correctly — the clause was never doing work.

## Where I'd sharpen your wording

"Any unrecoverable error (needs user input) is a hard bail" — "needs user input" is too wide. Gates need user input and aren't errors. I'd cut it to a three-class taxonomy, which also kills "half-applied handling" as a category outright:

1. **Outcomes** — states the document enumerates in a finished condition. The run continues. Nothing-to-release, a scan skipped, a config absent → `+Setup`. These are the "known branches" from your message, and they are not error handling.
2. **Errors** — states no step claims. Drain: report what happened and what state things are in, advise the manual fix, end the run, suggest an issue.
3. **There is no third class.** Recovery happens outside the run, by the user, and the fixed world re-enters through a clean invocation.

The reason this works — and why it's a genuinely agent-shaped convention rather than sloppy engineering — is that an agent can *describe* an unanticipated state in natural language to someone who can act on it. A program can't, so it must enumerate recovery. You're not skipping error handling; you're delegating it to the only party in the loop who can actually do it. (That's a *why* — it belongs in this conversation, not in the documents.)

## What I'd change upstream

Six edits, none large:

- `steps.md:127-133` — collapse Dispositions into one law + per-class report contents; delete the "destructive errors" scoping.
- `steps.md:118-125` — the error step's engagement line gains "and the manual repair that would let a clean re-run succeed".
- `conventions.md` — a new entry, **Hard bail and clean re-run**, sitting beside "The error step claims the remainder".
- `conventions.md:10` — drop "Half-applied states are part of the remainder"; the new entry covers it and more.
- `drafthorse/SKILL.md:46` — digest test widened from half-applied to any failure (this is Fix 15, now broader).
- `SKILL-template.md:144-146` + `drafthorse-saddler.md:136` — shipped text and the audit check, both widened to match.
