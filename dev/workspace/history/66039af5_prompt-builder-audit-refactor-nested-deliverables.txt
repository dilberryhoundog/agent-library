A capable agent maps that by name (plan→Tech Plan, code→Implement, review→Code Review). It breaks exactly where it matters most:
- **Approval gates** — nothing says which artefact must be on the table at stage 3. Agent may arrive with a sketch, or with code already written.
- **Non-obvious pairs** — "Research brief" + "Artifact" across Research / Concept / Spike: which stage produces the artifact? Guess.
- **Default agent behaviour** — with deliverables listed separately, agents tend to produce them all at the end, not as the run progresses. Same for Skills: "invoke when needed" is fine for self-describing skills, weak for the ones you want at a specific stage (e.g. `versioning` only at Ship).

**Recommendation: bind at the stage, keep the bundles as the pools**
- Each Process stage row gets two small pickers drawing from the existing option lists: *produces* (Output deliverable groups) and *uses* (Skills groups). Stored on the stage, emitted inline:
  ```
  2. Tech Plan → produces Implementation plan
  3. User Approval — stop, present the work, and wait for my explicit go before continuing
  4. Implement → produces Working code · uses dev-tools:git-box
  5. Code Review → produces Review
  ```
  Unambiguous for the agent, including what the gate is gating.
- Output builder becomes multi-select and means **what is handed back at the end of the run** + Depth; explainer says so. Stage-level outputs are the intermediates. Clean split, no overlap.
- Skills builder stays the pool the agent may use; stage *uses* pins timing. Architecture needs nothing — it's global.
