[ASSISTANT 💬]
Rewritten. Your model is the native one and it's cheaper than what I described.

**The mechanism:** `showSaveFilePicker({ id })` / `showOpenFilePicker({ id })`. The `id` string is a memory key — the browser records the picked directory against it, per origin, across sessions. Verified against the WICG spec's "determine the directory the picker will start in" algorithm:

- `id` ≤32 chars, `[A-Za-z0-9_-]`
- **Trap:** a `FileSystemHandle` passed as `startIn` outranks the id lookup and kills the memory. Don't pass one.
- **Omitting `id` is not neutral** — every id-less picker shares one slot, so export and import would overwrite each other's location. Distinct ids *are* the separation you asked for.
- A well-known `startIn` (`"documents"`) ranks *below* the id, so it's safe as a first-run-only default.

**Page stores nothing.** No IndexedDB, no `HANDLES` slot, no settings key, no Utilities field, no boot restore. Goal 3 dissolves — the browser does the persisting.

**Work:** two helpers (`saveJson`/`openJson`, ~10 lines each), 5 call sites, one new capability flag (`CAN_PICK` at :1771 tests `showOpenFilePicker` only — `showSaveFilePicker` is a separate function). Existing import handlers keep their bodies; `FileReader` becomes `File.text()`. `download()`/`fileInput()` stay as the Firefox/Safari tier.

**Two gotchas worth pre-empting:** cancel rejects with `AbortError` (page already has the guard idiom at :3117), and both pickers need transient activation — call the picker first in the handler, serialise inside the `.then`.
