## Mechanism — how "remotely referenced" actually works

Plugins can't borrow a skill from another repo; the unit of remote sourcing is a whole plugin. Realistic options:

1. **New repo = its own plugin `drafthorse`** (recommended). Marketplace entry `{"source":{"source":"github","repo":"dilberryhoundog/drafthorse"}}`. agent-tools keeps corpus-sweep, adds `"dependencies": ["drafthorse"]` in plugin.json → installing agent-tools auto-installs drafthorse (same marketplace, no cross-marketplace allowlist needed; version ranges need CC ≥ 2.1.110).
2. Git submodule under `extensions/skills/drafthorse` so symlinks keep working — **don't**. Plugin install clones the marketplace repo; submodules won't be initialised → empty skill dir in the cache.
3. CI copy-sync — two sources of truth. No.

[ASSISTANT 💬]
No apology needed — it's the right question to ask before moving one thing. My read:

## The real decision

Not "extract drafthorse?" — it's **what's the promotion path when a grab-bag skill becomes a product?** Decide that rule once; drafthorse, classroom, flightdeck all fall out of it.

## Options

**A. Everything stays here, products get a top-level tier**
- e.g. `products/drafthorse/`, `products/classroom/` each a self-contained plugin (own plugin.json, skills/, agents/, docs/, tests/), no `extensions/` symlinks; `plugins/` + `extensions/` remain the grab-bag.
- Pro: one checkout, one worktree root, shared test/orchestration harness, corpus-sweep sees everything, no invocation-ID churn, no cross-repo release dance.
- Con: history and issues stay mixed; "assets live in two places" — but that's a *tier*, not a mess, if the rule is crisp (product = own folder + own version; grab-bag = extensions+symlinks). Privacy impossible per-product (repo is one visibility).

**B. One repo per product** (what I outlined last turn)
- Pro: privacy per product, clean history, releases/tags natural, marketplace already supports github sources, product can outgrow CC (flightdeck as HTML suite is a real candidate).
- Con: orchestration/tests across products = multi-repo; corpus-sweep seams; N repos to keep in sync with the marketplace.

**C. Fold into dev-workspace** — no. dev-workspace is a git/workspace CLI; drafthorse is a doc framework. Different audience, different name, would confuse both READMEs. Only flightdeck *might* belong there if it's literally a dev-workspace UI — otherwise no.

## On your specific worries

- **Worktrees**: agent worktrees are per-repo, so multi-repo means an orchestration run over "all products" needs a wrapper (a meta-repo or a script that opens N worktrees). Not fatal but real friction — favours A.
- **Privacy**: the only thing that *forces* B. But you don't need it now; extracting later is cheap if the product is already a self-contained folder — `git filter-repo --path products/drafthorse` gives you the repo with full history in minutes. Requirement: no symlinks out of the folder, no citations into the rest of the repo. That's exactly the "installable citations" rule DraftHorse already enforces.
- **"Repo for all my agent assets"**: still true under A. B breaks it.

## Recommendation

**A now, B on demand.** Add a `products/` tier (or reuse `plugins/` and just stop symlinking for product plugins — fewer concepts). Rule: a product plugin owns its files outright; grab-bag plugins symlink from `extensions/`. Move drafthorse skill+agent+docs+rule into `products/drafthorse/` (or `plugins/drafthorse/`), update marketplace source to that path, agent-tools depends on it. corpus-sweep profile paths change once, stay in-repo. Tests/orchestration live under the product folder. When a product needs privacy or a life of its own, filter-repo it out and flip the marketplace entry to a github source — the layout is already extraction-ready, so that becomes a 1-hour job instead of a redesign.

The one thing I'd do *today* regardless: keep every product folder free of outward symlinks and repo-relative citations. That's the cheap insurance that keeps both doors open.

[ASSISTANT 💬]
Candidates, with the test being "reads correctly next to `plugins/` and `extensions/`":

- `products/` — says "this has users and a version"; slightly commercial-sounding but honest about the tier.
- `frameworks/` — fits drafthorse, wrong for classroom/flightdeck (they're apps, not frameworks). Too narrow.
- `assets/` — already means "thing a skill ships" (`skills/x/assets/`). Collides. Avoid.
- `packages/` — monorepo-standard (npm/pnpm), neutral, implies independent versioning and eventual extractability. Strongest generic fit.
- `standalone/` — states the rule directly (self-contained, no symlinks out, extraction-ready). Slightly awkward as a noun.
- `suites/` — good for classroom/flightdeck (multi-part), weak for drafthorse.
- `projects/` — clashes with `~/Projects` and reads as workspace, not artifact.
- `toolkits/` / `kits/` — friendly, but vague about the "owns its files" rule.
- `first-party/` / `core/` — describes provenance, not tier; everything here is first-party.

Pick: `packages/` if you want convention and neutrality; `standalone/` if you want the folder name to *be* the rule. I'd take `packages/`.

what is the name for when a plane has to go around again. aborted landing?

[ASSISTANT 💬]
**Go-around** — the standard term. The pilot aborts the approach, climbs, and re-enters the pattern for another attempt. "Missed approach" is the formal ATC/IFR name for the same manoeuvre (the published procedure the pilot flies after going around). "Rejected landing" / "balked landing" are the rarer variants, usually when it happens after touchdown was imminent or wheels already touched.

Maps cleanly to a run: a **go-around** is a retry from a checkpoint — the flight isn't grounded, it just didn't meet the landing criteria (a red light on the finish check) and loops back for another approach. Nice pair with grounded: grounded = never/no longer flying; go-around = still flying, trying again.
