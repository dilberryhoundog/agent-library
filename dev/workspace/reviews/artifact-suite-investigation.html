      Design system

      The Paper/Ink palette is already canonical and needs no design work: prompt-builder's 45 token declarations (14 colour/shadow tokens x 3 theme blocks, plus 3 type tokens) are byte-identical to paper-ink-fingerprint's, and five of the seven in-family files carry the same values. All real divergence lives one layer up, in the scaffold: seven files use five different .shell widths, three different h1 clamps, four different standfirst sizes, and five different prose measures; two files (both issue-45 artifacts) dropped the --serif/--disp/--mono tokens entirely and hardcode the font stacks. corpus-sweep-design is a foreign design system and should contribute nothing but its idea of diff tokens. The theme mechanism is the biggest gap: the three-tier CSS cascade is present in 6/7 files but only prompt-builder actually drives it. Lift prompt-builder's pre-paint script and toggle verbatim into the shell. Five feature-list surfaces have no tokens anywhere in the corpus: a diff gutter, a keep/context colour, filter-tag colours, a labelled quote block, and a recommended-option highlight; the cards name the exact tokens for each.

      Component catalogue

      Six of the eleven kickoff features already exist at exemplar quality and should be lifted almost verbatim: the shell (section-ledger's grid masthead/rail/main), the review card (issue-45-review's chiprow + colour sidebar + respond block), the options card (process-nesting-demo's .mode rows with a recommended badge), the issue breakdown (issue-45-review's masthead-meta + verdict-strip), the demo strip (mock-4-proposals' dashed .demo + .readout), and return prompting (section-ledger's generated attach() + collect(), which appears in four near-identical copies and must be hoisted into the shell once). Three features are partial and need rework: diffs put the +/- marker inside the content box; quoted conversation exists only as issue-45-diffs' .answered cards with no speaker attribution; link-to-site is effectively absent, with two outbound hrefs in the corpus, both the same GitHub issue. Two features have no precedent at all: interview pages and filterable tags. Two cross-cutting gaps block kickoff goals outright: nothing except prompt-builder persists anything, and every collect() emits a bare digest with no branch, issue or file provenance. Take corpus-sweep-design's SVG figures, stat tiles and details disclosure, retokenised, and ignore its styling.

      Scripting and state

      Two separate JS traditions, and neither meets the stated goal. The five review pages all run the same ~30-line script: generate or hand-author a radio group plus a textarea per card, then on Copy walk the DOM and emit Markdown, skipping items with no pick and no note. Nothing is ever persisted; a reload wipes every answer. prompt-builder is the only file with a real state layer and already contains all three primitives the suite needs (a DJB2 fingerprint of the agent-authored data, a localStorage overlay over it, and a dirty check), but its staleness policy discards the overlay when the file changes, which is backwards from "flagged, not lost". Card identity everywhere is ordinal, so any regeneration that inserts or reorders a card silently reassigns answers. Recommendation (open — decided in D-6, D-7, D-8 and D-9): one #page-meta JSON block and one localStorage document per page in the shell, answers keyed by agent-assigned content slugs, per-card fingerprints that mark a changed card stale instead of dropping its answer, "edited" defined against an explicit pre-checked default, and a return prompt that carries the provenance the mastheads already display.

      Architecture

      Ship a copyable shell, not a library. Roughly 30-40% of every review page's bytes are chrome the agent rewrites from scratch each time, and two independently written review pages share most of their CSS selectors, so the chrome is already a de-facto shared system, just re-typed each build. Make it literal: extensions/artifacts/suite/shell.html holds every token, layout rule, and the response/return-prompt engine; the agent creates a page with cp (zero tokens through the model) and then uses Edit to splice content into named marker comments, exactly as spliceBlock already splices JSON blocks in prompt-builder. Content is markup, not JSON; the repo's classroom skill already ships the alternative (self-contained HTML block partials with a leading instruction comment). Keep the response surface generated by the shell's JS from article ids so a card costs content only. Updates edit one card in place; never regenerate the whole file, because stable card ids are what let per-card localStorage preserve prior answers.

      Provenance and navigation

      Exactly three href forms exist across the references: in-page hash anchors, absolute GitHub issue URLs, and Google Fonts or favicon links in the head. There is not one file://, vscode://, or relative href anywhere; every file path is inert text, so the kickoff's first goal is entirely unbuilt. Provenance is better off: a de-facto eyebrow schema exists in three variants (kind/rev · issue · branch · base/commit · date), but only the issue is ever a link. The suite should ship one provenance JSON block per page that the shell reads once and derives every URL from, so per-card markup carries only data-path and data-lines. The link-to-site component must emit three parallel hrefs (relative for file://, vscode://file for the editor, GitHub blob for the web) gated on location.protocol, because relative disk links die on publish while GitHub links survive both. For navigation, the corpus has two ToC shapes and zero active-section highlight; the rail also disappears below 1040px with no fallback. Generate one list from section and article ids, drive it with an IntersectionObserver, and render it as a rail on wide viewports and, if D-2 goes the recommended way, a pill row on narrow ones.
