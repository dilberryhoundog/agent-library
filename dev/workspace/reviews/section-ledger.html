Where it lands, rev 2

problem, architecture, skills, agents, process, and now recipes all go in. goals stays. Rev 1 argued for cutting it on the premise that overlapping sections compete for one prompt — they do not. The page is a menu you draw from, so two sections covering adjacent ground is coverage, not duplication. That premise was doing quiet work under three findings; each is corrected below.

01Addproblem

Problem earns a section, on one condition

Task is an imperative — add a dry-run flag. Problem is a symptom and its cost — people run sync blind and find out what it restored afterwards. Those are genuinely different inputs, and the second is the one that lets an agent push back on the first. Without it, a wrong Task is executed faithfully.

The condition stands, but it is smaller than rev 1 made it. Sections are optional and you fill the ones you want — some sessions open with a task, others open with a symptom and no proposed fix. The blurbs still need to keep the two apart so that whichever one you reach for, you know it is the right one.

Reads interchangeable

"Describe the problem you are solving."

Reads distinct

"What is happening now, who it costs, and how you noticed. No proposed fix — that is Task."

Output order: Task first, Problem second when both are filled. An agent anchors hardest on what it reads first, and that should be the instruction rather than the backstory. When only Problem is filled it lands first by default, which is the right behaviour for a session that opens with a symptom.

02CutWithdrawngoals

Adding Problem is what kills Goals

Withdrawn. The argument assumed every section competes for room in one prompt, so two sections covering adjacent ground meant the emitted text would say the same thing twice. That is not how the page works — sections are optional, you fill what the session needs, and a page holding both Problem and Goals costs a tile rather than a repetition.

The failure mode I was guarding against does not survive the correction either. Three fields inviting the same sentence is only a problem if you are obliged to fill all three. You are not.

Goals stays, unchanged, and earns its keep on exactly the larger sessions where you want the outcome stated separately from the pain and separately from the test.

03Reworkverify

Goals and acceptance criteria are not the same thing — but only one of them belongs here

Three distinct ideas hide in the current wording, and separating them settles the question:

  • Goal — the outcome, in prose. Not falsifiable on its own. People should see what sync will restore before it runs.
  • Acceptance criterion — binary, checkable, no judgement needed. The flag writes zero bytes.
  • Verification — the procedure that produces the evidence. Run it against a dirty tree, paste the output.

So: not the same thing, and all three stay. What changes is only which section holds which — right now Goals is labelled "Criteria" and blurbed as success criteria, which points its field at the wrong one of the three.

Now — Goals wearing Verification's label

goals.items "Criteria", blurbed "Success criteria. The agent checks its own work against these."

Next — each field says what it is

goals.items "Outcomes" · verify.criteria "Acceptance criteria" · verify.gates · verify.items "How to check"

Goals keeps its list widget and gets a blurb about outcomes rather than criteria. Verification gains the criteria field it was already describing. No section moves, no section goes.

04Addarchitecturereading corrected

Architecture splits cleanly from Output — and it is prescriptive, not descriptive

Output currently carries stack, which does not belong to it. Output describes the reply: what comes back and how much prose wraps it. Architecture prescribes the build: what to use, so the agent stops guessing. That last word settles the ambiguity rev 1 left open — this is not a description of what exists, it is an instruction about what to reach for.

The shift changes the fields. A descriptive section would ask you to survey the codebase; a prescriptive one gives you lists to pick from, because you already know what you want used.

Every field but the last is picks-plus-free-text, so the common case is four clicks and the uncommon one still has somewhere to go. Propose an architecture remains a Deliverable value in Output, where it does not collide with this.

05Addskillsrecipes

Skills chooser — the widget is easy, the list is the problem

Grouped multi-select, one group per plugin. Emit invocations rather than names, because the target session acts on the slash form:

## Skills - Read markdown before drafting the document - Run /dev-tools:versioning to cut the release

The real question is where the list comes from. A local HTML file cannot read your installed plugins, so the options are hand-maintained in the JSON block and will drift the first time you add a plugin. Two ways out, both cheap:

  • Regenerate on demand — a small script walks plugins/ and extensions/skills/, prints a JSON fragment, you paste it. Drift becomes a deliberate refresh rather than a slow rot.
  • Free-text escape — a "other skill" text row alongside the chips, so an unlisted skill never blocks you.

Ship both — you called hand-maintained, and the text row is what makes that safe. The chips cover the skills you reach for weekly; the text row covers everything else.

Omakase prompts are a separate section, and the refactor is smaller than it looks

A skill and a recipe are not the same mechanism. Picking markdown emits a reference the agent resolves on its end. A recipe emits its own prose verbatim — the text is the payload. Putting them in one section means one widget doing two jobs and a chip whose behaviour you cannot predict from looking at it.

So: recipes, its own tile. Read-only blocks you toggle on. The layout problem you sensed is real but narrow — a recipe's whole value is its wording, so you have to be able to read it before enabling it. A chip cannot show a paragraph. The section page shows each recipe as a card with its text visible in full, monospace, unselectable, and a toggle in the corner. That is a new field kind and no change to anything around it.

A starter set worth having, drawn from what this repository already asks of agents:

RecipeDoesPosition

The position column is what makes Update this tool work without a preset system. That recipe is effectively a whole prompt — you would toggle it and leave every other section blank. Since empty sections already vanish, the emitted text is just the recipe, sitting first. No mode switch, no form that replaces the form. Each recipe declares first or last in the JSON and the renderer honours it.

One consequence to accept deliberately: recipes are the only place where the page ships prose you did not write. Keep the texts short enough to read in one glance, or the read-only card becomes a wall you toggle without reading — which is the failure this section exists to avoid.

06Addagents

Agent teams is two fields, not one — roster and shape

"Which agents" and "how they run" are independent choices, and picking only the first produces a prompt that reads as a list of names with no instruction attached.

Roster — grouped multi

Explore · Plan · general-purpose · doc-reviewer · drafthorse-saddler · breaking-change-detector · git-robot · course-researcher

Shape — single select

Solo · Parallel fan-out · Pipeline · Judge panel · Adversarial verify

The shape vocabulary is worth taking seriously — those five are the orchestration patterns that actually differ in outcome, and naming one tells the agent more than naming three subagents does.

One caveat to put in the blurb: this section only pays off when the receiving session can spawn agents. Emitting nothing when empty already handles the rest.

07Addprocesslargest build

Process chooser changes what the page is for

Every other section describes the work. Process describes the run — it turns a paragraph into a sequence with checkpoints in it. For anything longer than one edit it is the highest-leverage field on the page, and User Approval sitting at position four is the whole reason why.

This is also the one place where numbering is not decoration. Order carries meaning here, so the emitted list is numbered and the widget shows positions:

01Investigate→ 02Concept→ 03Tech Plan→ 04User Approval→ 05Implement→ 06Test→ 07Commit Work→ 08Github PR

Three build decisions worth making before code:

  • Duplicates are allowed. Test before review and test after review is a normal shape. That means each placed stage needs its own instance identity, not just a label — otherwise removing the second Test removes the first.
  • Drag needs a keyboard twin. Native HTML5 drag-and-drop works and is entirely unusable without a mouse. Pair it with Alt + ↑/↓ on a focused stage, and let clicking a palette chip append rather than requiring a drag at all. The drag becomes the fast path, not the only path.
  • Stages take notes. A bare User Approval is weaker than User Approval — show the file list before writing. One optional inline note per placed stage, emitted after an em dash.
08Restructuredashboard

Two groups, not three — the writing ones and the choosing ones

Sixteen tiles is a search task. Rev 1 proposed three phase-of-work groups; your split is better and I am taking it. Phases are a story about how a prompt gets written, which is a story that changes every session. Write versus Choose is a property of the tile itself and never moves.

It also encodes something the phase grouping could not: cost. A Write tile asks for sentences and a minute of thought. A Choose tile asks for three clicks. Scanning the dashboard tells you what a fuller prompt would actually cost you, which is the question you are asking when you scan it.

Mixed sections sit with their primary field. Constraints has a free-text box under its chips and still belongs in Choose, because the chips are what you use. Verification has chips for gates and still belongs in Write, because the criteria and checks are where the work is.

09Restructureoutput order

Dashboard order and prompt order stop being the same list

Right now the array does both jobs. Grouping breaks that: the order you fill sections in is not the order they should reach the agent. Problem is written before Task and read after it. Guardrails are filled early and belong last, where they are still in view when the agent starts working.

Cheap fix — give each section an explicit order number used only by the renderer, and let array position drive the dashboard. Two numbers, no new machinery.

Open questions

5

Each carries a recommendation. Silence on any of them means I build the recommendation.

1 · What does the self-update recipe actually say?

It is the recipe that prompted the section and the only one whose wording I cannot guess. It has to tell an agent where the file is, what "current state of play" means, and what to leave alone — the hand-editable JSON blocks in particular.

Recommend: I draft it, you edit it in place. Faster than specifying it in the abstract, and the draft is throwaway if it reads wrong.

2 · Do recipe texts duplicate the repository's rules, or point at them?

Durable-document rules and the workspace protocol already exist as files. A recipe can restate them or say "read extensions/rules/durable-documents.md".

Recommend: point, with one line of gist. The pointer never goes stale and the gist tells you what you enabled without opening anything.

3 · What fills the Architecture pick lists?

The section is prescriptive, so the lists have to hold what you actually build with. I can seed them from this repository — plain HTML, JavaScript without a build step, Node for scripts, markdown — but that is one project's vocabulary and you prompt across more than one.

Recommend: seed broad, prune later. An unused chip costs a glance; a missing one costs a trip to the free-text box.

4 · Do process stages carry agents?

Carried over — unanswered in rev 1. A placed stage could name the agent that runs it, Investigate → Explore. It is the natural join between two of the new sections and it doubles the pipeline widget's complexity.

Recommend: not in mock 2. Ship the note field first; if you find yourself typing agent names into notes, that is the signal.

5 · How much of this lands in mock 2?

Six new sections, three new field kinds, a regrouped dashboard, and a split output order. That is a full rebuild of the page rather than an edit to it.

Recommend: all of it, one pass. The regroup and the order split touch every section anyway, so staging it means doing that work twice.
