Export where you point

Export drops a file in the browser's download folder. Import opens a dialog wherever the browser last happened to be. Both are fixed by swapping two helpers for the two pickers the platform already provides — and by handing each picker back the handle it returned last time, which is the one form of memory that survives a page opened from disk.

      F1no setup step

      Nothing to configure, nothing in the file

      No settings key, no folder-picker field in Utilities, no "choose a folder before this button works", and nothing that can fall out of sync with the loadout. The page keeps one thing per button — the handle the picker last returned — in the IndexedDB store it already runs, and refills it at boot.

      Every button is usable on first press. The remembered folder is a consequence of using it, not a prerequisite.

      How the picker remembers

      verified against the spec

      The behaviour is specified, not a Chromium accident. The File System Access spec defines an ordered algorithm for choosing the directory a picker starts in, and two of its steps decide whether this works.

      1. Validate id — ASCII letters, digits, _ and - only, 32 characters maximum.
      2. If startIn is a FileSystemHandle, it wins outright and the remembered directory is never consulted. A file handle resolves to the directory holding it.This step is what the page uses. Hand back the handle the picker returned last time and it reopens in that file's folder.
      3. If id is given, the recently-picked-directory map for this origin is checked.Measured not to hold in Chrome — see below. This was the first implementation, and it silently does nothing.
      4. Otherwise, if startIn names a well-known directory (documents, downloads, desktop, …), that is used.
      5. Otherwise, with no id, the map is checked under the empty-string key.
      6. Otherwise, a user-agent default path — Documents, in practice.
      F2measured

      Step 3 does not hold in Chrome; step 2 does

      A standalone page — dev/workspace/filebox/picker-demo.html — ran the three strategies side by side, each with its own picker id and its own stored handles, saving and opening a dummy object and logging every option passed. The result, across reloads:

      StrategyWhat it passesReopens where you left it
      id only{ id }✕ back to the default folder every time
      handle{ startIn: handle }✓ remembers
      both{ id, startIn: handle }✓ remembers

      So the handle carries the folder and the id carries nothing. Both is what the page ships: the handle does the work, and the id stays on the call as a second line for the case where the stored handle is dropped — one property, and the only thing left if IndexedDB is ever cleared.

      F3testing trap

      An attached debugger silently eats the dialog

      While a Chrome DevTools Protocol client is attached — Playwright, Puppeteer, or any automation driving the browser — file-chooser dialogs are intercepted and dismissed before they appear. The picker then rejects with:

      AbortError: Failed to execute 'showSaveFilePicker' on 'Window':
Intercepted by Page.setInterceptFileChooserDialog().

      Because AbortError is the same name a genuine cancel produces, and a cancel is deliberately silent, the button looks completely inert — no dialog, no message, no console error. The interception applies to the whole browser, not only the automated tab.

      Test the pickers by hand, with nothing attached. Any measurement of this feature taken while automation is connected is worthless, and looks exactly like a broken button.
      What follows from that

      The remembered handle must be read synchronously. Both pickers require transient user activation, so an await between the click and the call risks spending it. The handles are cached in memory and refilled from IndexedDB at boot, so the click path never waits on storage.

      A remembered file can be moved or deleted. That makes startIn throw, so the call is retried once without it and the picker falls back on its own defaults. A cancel is not retried.

      A handle returned by a picker arrives already granted. The allowed() re-check at line 1806 exists for handles restored from IndexedDB; nothing on this path needs it, and startIn only reads the path.

      The two replacements

      helpers, then 5 call sites

      Both new helpers return promises and both reject with AbortError when the user cancels. The page already has the idiom for swallowing that — if (e && e.name !== "AbortError") appears at lines 3117 and 3280.

      The memory — one handle per picker id
      // Read synchronously: an await here would spend the user activation
// both pickers require. IndexedDB only refills the cache at boot.
var LAST_PICK = {};

function rememberPick(id, handle) {
  LAST_PICK[id] = handle;
  idbPut("pick:" + id, handle);
  return handle;
}

// A remembered file that has since moved makes startIn throw, so the
// retry drops it and lets the picker fall back on its own.
function pick(name, opts) {
  var startIn = LAST_PICK[opts.id];
  if (startIn) opts.startIn = startIn;
  return window[name](opts).catch(function (e) {
    if (!startIn || (e && e.name === "AbortError")) throw e;
    delete opts.startIn;
    return window[name](opts);
  });
}

      The four ids

      settled

      Each payload gets its own save and open memory, because a working prompt and a shared loadout do not live in the same place. A prompt export is scratch, tied to one job, and belongs beside the project it came from. A loadout is a configuration you keep and hand around.
