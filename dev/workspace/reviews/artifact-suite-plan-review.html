What ships

The plan's deliverable is one skill directory of seventeen files, symlinked into an existing plugin and released as a minor version. These cards settle the package boundary — what is a file, where built pages land, and which two Python scripts do all the writing.

Where the plan landed

One skill, extensions/skills/artifact-suite/, ships a copyable page shell plus three page templates, three card-level blocks and a DraftHorse build procedure. The shell carries tokens, three layouts, a generated table of contents, a tag filter bar, a three-way theme control and one engine script. Content is spliced into seven marked regions by splice.py; the agent never opens the shell and never writes chrome.

This review page is itself built to that specification — the eyebrow above, the contents rail, the filter bar, every reference block, the diff, the figure and the floating Copy prompt pair are the plan's own components, running.

01Integratepackaging

One skill, not a plugin of its own

Everything lands in extensions/skills/artifact-suite/: SKILL.md, three assets/ scripts, three assets/blocks/ files, three assets/templates/ files, four references/ files and three tests/fixtures/ pages. Seventeen files plus one symlink — one release unit.

02Integratepaths

Built pages land in dev/workspace/artifacts/

The file name is <id>.html where id is #page-meta.id. dev/workspace/reviews/ keeps its documented meaning — reviews of completed work — and holds the Stage 1 corpus. Both directories archive into dev/branches/<branch>/ identically, so the mirror route works for either.

Before any copy, ls dev/workspace/artifacts dev/branches/*/artifacts confirms the id is unused: on file:// every local page shares one origin, so a duplicate id silently merges two pages' stored answers.

03Integratetooling

splice.py is the only thing that writes a page

About ninety lines, seven forms: fill a marker region from stdin or by lifting a named part out of a template or block file; replace one card by id; append a card before a section's closing tag; set the layout class on .shell; and two read-only forms, show page-meta and show cards. It asserts each marker appears exactly once and refuses a second insert of the same sourced part.

The refusal is byte-level: the lifted content with delimiters stripped and trailing whitespace normalised is tested against the page; a hit exits 0 with already present on stderr and writes nothing.

04Integratetooling

verify.py runs the static tier as one command

About 120 lines implementing checks S1-S10 as subcommands of a single script, run as python3 $S/verify.py <page> --static. It also writes the doctype-wrapped copy that runtime check V6a serves. It exits non-zero on the first failing check, naming it.

05Integraterelease

Symlinked into chat-tools, released as 2.2.0

plugins/chat-tools/skills/artifact-suite -> ../../../extensions/skills/artifact-suite. chat-tools already holds markdown, whose output this is the HTML counterpart of; agent-tools is harness-extension authoring and dev-tools is git and releases. Release runs through /dev-tools:versioning, which resolves symlink targets at runtime.

Plugin assets run from the last installed release, so through Stage 3 the skill is executed by hand from the working tree. The release is cut only after the acceptance test passes.

06Integrateskill

The skill is a DraftHorse procedure

harness-format: DraftHorse, matching classroom, corpus-sweep and versioning. Body: global invariants, inline references (marker table, landing rule, token economy, six-kind mapping), ten steps and a terms list. 260-320 lines.

Both invocation fields are omitted, so the skill is model-invocable and user-invocable — the agent reaches for it before hand-authoring chrome.

The shell

One file, copied per page, carrying every byte of chrome. A 36KB hard ceiling with a 32KB target: CSS ≤ 16KB, engine ≤ 17KB, head and scaffold ≤ 3KB. These cards cover its form, its editable regions and each piece of furniture it owns.

07Integrateform

The shell is a bare fragment, no doctype

No <!doctype>, <html>, <head> or <body>. Chrome builds the missing structure from file://; the Artifact tool supplies its own skeleton, so one file serves both. The cost is quirks mode on disk, and the shell is written to avoid all four differences that matter: lowercase class and id names only, explicit font and line-height on td/th, no percentage heights, no image inside a table.

Non-ASCII glyphs in CSS content are written as escapes (\2212, \00B7) because the fragment's <meta charset> is inert under the wrapper. A cheaper cure — ship a doctype and strip it at publish — is open as question Q4 below.

This review page carries a doctype and a full document, because it is hand-authored rather than built by the suite. Its rendering is standards mode; the shell's would be quirks mode from disk.

08Integrateform

Seven marked regions, filled two ways

HTML regions are <!-- @name --> … <!-- @name:end -->; the one region inside <style> uses /* @template-style */. Three placeholder regions — @doc-title, @page-meta, @masthead — ship one element each and are replaced whole, so a page never ends with two titles or two meta blocks. Four empty regions — @template-style, @content, @sidebar, @template-script — take content appended before their closing marker, which therefore survives the next splice.

Placeholder regionEverything between the markers is replaced. Written once, never appended to.
Empty regionContent replaces the closing marker, followed by the same closing marker. Appended to repeatedly.

layout, card, section and show are reserved keywords and never marker names.

09Integratelayout

Three layouts; one writable attribute outside the markers

.shell at 940px, .shell.rail at 1180px with a 232px contents column from 1040px, .shell.board at 1340px with a 440px sticky sidebar from 1060px. The class attribute on the single .shell element is the only byte outside a marker a page may change, and only through splice.py <page> layout rail|board.

Name collision rule: the shell never defines a bare .rail selector — every rail rule is .shell.rail, so .rail stays free for the folder-picker row pattern it already names elsewhere.

11Integratedesign system

Type triple declared once; two prose measures

--serif, --disp and --mono are declared on bare :root and no template or block ever names a font family. Body is 17px on --serif at 1.6. Two prose measures, set once: 68ch on .card p, .card ul, .card ol and .sec-intro; 62ch on .standfirst, .gloss and blockquote.

12Integratecss

:has() is allowed, with one load-bearing floor

The target is Chrome from file://, where :has() shipped in 105. A :has() rule may only add a visual state the native control already expresses, and never shares a selector list with a non-:has() selector. One exception is load-bearing — .verdicts label:has(input:checked) is the only expression of a verdict, because .verdicts input is visually removed — so the shell carries an @supports not (selector(:has(*))) floor that restores the raw radios directly beneath it.

13Integratenavigation

One contents model, two surfaces

The engine builds one group per section[id] labelled from its .sec-head h2, and one entry per article.card[id] labelled from its .chip.id text plus h3, falling back to the h3 alone where a card carries no id chip. It renders that model into both containers: the 232px sticky column shown only in .shell.rail at ≥ 1040px, and the sticky pill row shown everywhere else. No viewport lacks navigation.

A single IntersectionObserver with rootMargin: -20% 0px -70% 0px sets aria-current="true" on the matching link in both surfaces at once. scroll-margin-top is 72px to clear the pill row, dropping to 24px only where the pill row is hidden.

Both surfaces on this page are generated from the cards below — scroll and watch the highlight track in the rail.

14Integratenavigation

A section id is permanent, exactly as a card id is

A <section>'s id is a lowercase slug of its .sec-head h2. It anchors the contents group, receives the :target ring, and keys that section's comment under sections in the stored document. Once published it cannot change without orphaning a stored comment.

15Integratefilters

Three tags, two states, one vocabulary

integrate, yourcall, defer appear identically in the markup attribute, the chip modifier and the card edge modifier, so they cannot disagree. The card declares data-tag on the <article>; the edge is a border-left driven by that attribute, never a second class the agent must keep in sync.

The filter bar is shell furniture, ships hidden, and reveals itself when the page carries two or more distinct tags. Each button's count is computed from the DOM. all and unanswered are states, not tags: they carry no chip, no card edge and no markup attribute, so the three-word vocabulary still governs everything printed. Filtering toggles hidden on non-matching articles and their contents entries, and the return prompt ignores it entirely.

The bar above this section is live. Unanswered is the one to work through a long page with.

.chiprow, then h3, then an optional blockquote, then prose and evidence blocks, then the engine's .respond last. Review, options and issue-breakdown pages share this anatomy exactly; what differs between them is the verdict vocabulary as data, the chips, and which optional blocks appear.

The id chip is written as an anchor to its own card — <a class="chip id" href="#storage-key-scheme">03</a>. The chip text stays ordinal for the reader; the fragment is the subject-named id. Click one and the :target ring confirms the landing.

20Integratecontract

A published class inventory, and a reserved list

Every class the shell owns is listed with its purpose and who writes it — agent, shell or engine. Reserved for demos and blocks to avoid: every shell id, data-theme, every token, and every shell class — .status, .card, .chip, .respond, .toc, .filters, .floater included — even where the shell's own rule is scoped elsewhere.

Runtime & state

One engine IIFE at the foot of the shell, in prompt-builder's dialect — var, function declarations, string concatenation, no arrow functions, template literals, optional chaining or class. It generates every response surface, persists one document per page, and composes the return prompt.

21Integratedata

One #page-meta JSON block, and prose stays in markup

The sole agent-authored data surface: id, kind, rev, title, a provenance object, a prompt.heading and a next array. Unknown keys are ignored. Any </ inside a string is written <\/, because a literal </ ends the script block.

readMeta() parses it once into META; on failure it flashes a red notice and falls back to a safe stub so the page still works.

22Integratedata

Verdict vocabulary lives on the card, not in the JSON

The Stage 1 review placed per-card option sets in #page-meta; the plan overrules that. They live on the <article> as data-verdicts="Agree|Revise|Reject", beside the card they govern, because a card-keyed map in JSON drifts from the cards it names. #page-meta therefore carries nothing per-card at all.

var DEFAULT_VERDICTS = {review: ["Agree", "Revise", "Reject"], issue: ["Accept", "Amend", "Defer"], options: [], interview: [], demo: []};

An empty resolved set yields a comment-only .respond. Options and interview cards always carry data-verdicts or data-answer="options", because their options are the page's content.

23Integratecontract

A card id names its subject and is permanent

The id attribute is an agent-assigned kebab slug naming what the card is about — id="storage-key-scheme" — never a position. One attribute serves storage, the radio group name, the contents anchor and the deep link. A stable identifier the subject already carries outside the page (ds-1, issue-45) is a valid card id; a counter of the card's place on the page is not.

validateCards() runs first in boot(): a card without an id gets a console warning, class needs-id and no response surface; a card whose id matches /^[a-z]?\d+$/i gets a warning naming the ordinal hazard but is still wired.

24Integrateengine

The engine writes every input on the page

attachRespond(card) appends the radios, textarea and Clear button as the card's last child, returning early where a .respond already exists or the card carries data-answer="none". The radio group name is v-<cardId>. The agent writes the article, the chiprow, the heading and the prose, and nothing else.

Events are delegated from document — one change, one input, one click — dispatching on closest("[data-card],[data-section],[data-filter],[data-held]"). Every response surface on this page arrived that way.

25Integratestorage

One stored document per page, keyed by page id

artifact-suite.page.<id> holds a single JSON document — schema, pageId, rev, savedAt, and maps of cards, sections and orphans. Read once at boot, written once per debounced change at 200ms. On file:// every local page shares one origin, which is exactly why the key carries the page id.

Accessors are prompt-builder's readStore / writeStore / dropStore, each wrapped in try/catch with an in-memory fallback map. Where storage is refused outright, the foot renders a warning: This browser is not saving answers — copy the prompt before you close the page.

26Integratestorage

Per-card fingerprints raise the amber changed strip

fingerprintOf(card) clones the card, removes .respond, .changed and .chip.earlier, then hashes normalised text plus data-tag plus data-verdicts with prompt-builder's DJB2. Per card, never per file — a whole-file rewrite that raises the strip on every card is a defect, not a feature.

Normalised text rather than innerHTML, so re-indenting during an unrelated edit does not read as a change, while every prose, option and tag change still is. Equal fingerprint restores silently with an Answered earlier chip; a different one restores and inserts the amber strip with a Dismiss button. Dismiss re-fingerprints and leaves touched alone.

27Your calldefect found

The specified boot order fingerprints too early

Building this page surfaced a real defect in the plan's own boot sequence. boot() runs restoreCard — which fingerprints — before expandRef and before any block or demo script has filled its container. A card holding a reference or a demo therefore hashes one way when the answer is recorded, after boot has finished, and a different way on the next load, before the reference has been expanded. Every such card shows the amber strip on reload with nothing having changed.

It reproduced here on the first reload, on the storage-document card, which holds a reference. On the acceptance rebuild it would fire on all 75 cards at once, since every finding carries evidence — and check V12 would only catch it after the whole shell was written.

Strip generated regionsExclude .ref-links, a reference summary and any .demo from the clone alongside .respond. The hash then covers authored prose alone and is order-independent.
Fix the boot orderMove expandRef, the block wiring and the demo wiring above restoreCard. Cheaper, but any future generator added below restore reintroduces it.

This page runs the first option; its fingerprints are stable across reloads. A live demo of the function is on the card above.

28Integratestorage

An answer to a removed card is held, not dropped

collectOrphans() moves every stored id with no matching card into orphans, keeping its last title, and renders a note in the foot: N answers held for cards no longer on this page, with Show and Discard. When a card returns under the same id its orphan moves back into cards and is marked changed.

A held answer also enters the return prompt as a Held: line naming the ids — a prompt carrying nothing but that line is still emitted, because a held answer is a fact the agent needs.

29Integrateprompt

Only touched cards enter the return prompt

touched flips true on the first genuine change on a card's radios or input on its textarea. A pre-checked recommendation left alone stays untouched and stays out of the prompt — which is precisely the kickoff's requirement that history be preserved without re-entering the prompt unless edited.

Affirmation is carried by the click handler rather than change: clicking an already-checked radio fires no change event, so the click handler records it anyway. Recording a value the card already holds is a no-op apart from touched — which is the point. A deliberate click on the recommendation is a decision; a card left alone is not.

30Integrateprompt

Accept all agrees every untouched recommendation

For every card carrying data-recommended whose entry is untouched, set the recommended verdict, mark it touched, stamp the time and revision, save, then report N cards recorded as agreed; M without a recommendation skipped. The button is shown only where at least one card carries a recommendation.

31Integrateprompt

The return prompt has one exact shape

Heading from prompt.heading; a Source: line joining page file, branch, issue or PR, revision and build date with a middle dot; an Untouched: line of two bare counts naming no card; a Held: line where orphans exist; ### Decisions listing touched cards in document order as **<cardId> · <h3 text>**; then ### Next from META.next; then a Re-open: line.

Multi-line notes survive: one line emits - Note: text, many emit - Note: then each line indented two spaces with empty lines emitted bare, so paragraph breaks reach the agent intact. A radio token is never upper-cased. Nothing answered yields the empty string, and Copy says so rather than writing an empty prompt.

Provenance & links

Every URL on a page is derived at load from #page-meta.provenance — no template ever writes a literal href. This is the half of the plan that answers the kickoff's first two goals: navigate straight to the file in question, and see where the work originates.

37Integratelinks

Four URL templates, one encoder

encPath(p) percent-encodes each path segment; line suffixes append after encoding. Disk is file:// over the absolute checkout root with no line fragment, since a markdown file over file:// has no line anchors. Editor is vscode://file<abs>:<line>. GitHub is a blob URL pinned to a ref. Issue, PR, branch and commit are the four obvious repository URLs.

The Stage 1 review proposed a relative-root prefix; the plan drops it. The absolute checkout path is accepted, so the disk href is file:// over that root and nothing in the suite emits a relative file href.

38Integratelinks

The agent writes attributes; the engine builds the reference

One empty element carries everything: data-path or data-url, optional data-lines, data-loc, data-branch, data-commit, data-label. The engine expands it into a collapsed disclosure whose summary shows the path, a line badge and a locator, and whose body holds Open file, Editor, GitHub and Copy path.

<details class="ref" data-path="docs/drafthorse/framework/steps.md" data-lines="111-128" data-loc="§ Dispositions"></details>

A reference carries data-path or data-url, never both and never neither; violating that renders a broken-state reference with a red edge, no chips and a console warning. A malformed data-lines is treated as absent. A diff block is always preceded by a reference naming its file.

Every reference on this page is one of these, expanded at load. Open one — the chips are real and point at real files in this checkout.

39Integratelinks

CSS alone decides which chip is primary

The pre-paint script sets data-origin="disk" or "web" on the root element. Two CSS rules then hide what cannot work and fill exactly one chip per reference: from disk, Open file is solid; from the web, the disk and editor chips are gone and GitHub is solid. A page published from disk therefore needs no rebuild.

One gap worth a decision: the two rules hide .ref-disk on the web but leave .ref-editor showing. A published page therefore offers a vscode:// link built from the author's absolute checkout path, which works on exactly one machine. Hiding the editor chip alongside the disk chip on the web costs one selector.

40Integratelinks

Other branches route through the archive mirror

43Integrateverification

Every printed path must be a link, and must exist

auditPaths() runs last in provenance: any .path element outside a reference gets a dotted amber underline and a console warning, so a path printed as inert text is visible as a defect rather than passing quietly.

At build time the path check confirms each data-path resolves to a file that exists, that the end of data-lines is within that file's line count, that a mirrored reference with no mirror is instead reachable by git cat-file -e <branch>:<path>, and that every data-url is https. Any output other than OK is a build failure.

Demo reads no page template at all: it reads the kit, whose last part supplies a page scaffold and a meta exemplar so a demo page has the same authoring floor as any other.

  • options — .shell up to eight cards, .shell.rail from nine; option rows instead of verdicts
  • issue — .shell.rail, verdicts Accept / Amend / Defer, stats or masthead meta, a verdict strip

55Integratedemos

The demo kit is a kit, not a template

A demo has no fixed shape. Procedure & verification

The build is ten DraftHorse steps and thirty-one checks in two tiers. This is where the token-economy promise is actually kept: the agent types cards and nothing else.

56Integrateprocedure

Ten steps, with the error step standing alone

Open the build; load the page kind; resolve provenance; instantiate the shell by copying it; splice the template; write the cards; revise a published page (dormant); verify; hand over; handle a build problem. Each is its own heading with its own start and finish conditions.

57Integrateprocedure

The agent never opens the shell or the page copy

A page is created by cp, never by writing chrome. Every subsequent write goes through splice.py under Bash. Read and Edit are not granted, because both refuse a path they have not read in the same session, and reading the copy would pull the whole shell back into context — which is the exact cost the design exists to avoid.

The page's own state is read back only through the two read-only forms, show page-meta and show cards.

58Integrateprocedure

A revision touches only the cards that changed

Open with the two show forms to read the current revision, the meta body and the ids already on the page. Published ids are permanent; a dropped card becomes withdrawn; only changed cards are spliced. The revision bumps by one, and date, build stamp and commit update in the same meta splice. The resulting git diff touches the meta block and the edited cards, and nothing else.

This is what makes the fingerprint honest: a whole-file rewrite would raise the changed strip on every card at once.

59Integrateprocedure

Roughly ninety-five authored lines for a ten-card review

Never typed: tokens, layout rules and the engine (supplied by the copy); the response surfaces, contents, pill row, filter bar and theme control (supplied by the engine); every file, editor and GitHub URL (derived from attributes and provenance); the eyebrow markup; the return prompt text; a template's scoped CSS and a block's CSS and script (lifted by splice.py, never read); and a whole file on update.

The measure the plan sets: about 95 authored lines and 8-10KB for a ten-card review, none of it chrome, against 3-4K output tokens of chrome per page under hand-authoring.

60Integrateverification

Ten static checks, no browser

No document tags and a shell stamp on line 1; all seven marker pairs present exactly once; the meta block parses and carries its seven keys; every card has a unique, non-ordinal id; option cards agree with themselves and every printed path sits inside a reference; no host but the two font hosts and no literal href anywhere; exactly one title, one h1, one meta block and no surviving placeholder; exactly one shell element with a permitted class; every spliced part byte-identical to its source; every card inside a section with an id.

61Integrateverification

Twenty-one runtime checks over a local server

Playwright over python3 -m http.server bound to loopback, with the pid recorded and killed at the end. They cover a clean console; generated counts matching card counts; theme; the pre-paint script's position; persistence across reload with line breaks intact; the storage key prefix; Clear; the empty and one-answer prompts; Accept all; the changed strip on exactly one mutated card; held answers and their recovery; loose section comments; every reference route and chip; four viewport widths with no horizontal scroll; each filter; a deleted clipboard API; the contents highlight; and the deliberate click on an already-checked recommendation.

One check is unusual and worth keeping: the same fixture is served twice, bare and wrapped in a doctype, and the two must render byte-identically at 1100px — the wrapper standing in for the Artifact tool's skeleton, so quirks mode is proved harmless without publishing anything.

62Integrateverification

Three frozen fixtures are the regression suite

A review, an interview and a demo page with frozen provenance — a zero commit, a fixed date, a branch named fixture. After any change to the shell, a template or a block, both tiers run over all three before committing. A fixture that must change to keep passing is a contract change, and is re-committed with the shell change that caused it.

Whether they ship inside the released plugin payload is question Q3 below.

65Integraterisk

Seven risks, each with its stated response

  • Shell budget — measured at ~15.5KB CSS plus an engine of ~54 functions; if the engine overruns 17KB, move the reference CSS and its expander into a block before cutting any behaviour.
  • Storage on file:// — two Stage 1 findings disagree on whether Chrome throws; the runtime tier therefore runs over localhost, with the memory fallback and the foot warning covering the throwing case. Check once by hand from disk during WP-2.
  • :has() with no fallback beyond the verdict floor — acceptable for Chrome; re-check if ever published.
  • Quirks mode from disk — the four differences are avoided by construction; a doctype stripped at publish would remove the risk outright.
  • Absolute checkout path in the meta block — see root-path-exposure.
  • Fingerprint blind spot — attribute-only edits other than the tag and the vocabulary do not raise the strip; changing a recommendation alone goes unnoticed.
  • Broad kill grant and a model-invocable description that could fire on unrelated HTML work — both bounded by wording rather than by mechanism.

Unresolved questions

Five owner review items. The plan's body value stands and Stage 3 builds against it unless you overrule it here — so each card's pre-checked option, where there is one, is what happens if you say nothing. Two carry no recommendation, because the plan takes no position.

Q1Your callbudget

The shell budget more than doubled

Stage 1 sized the shell at 14-18KB, before persistence, contents, filters and provenance were in scope. Measured against this plan's own rules it comes out near 15.5KB of CSS plus an engine of roughly 54 functions, so the plan sets the ceiling at 36KB hard with a 32KB target. A ten-card page then lands near 48KB, well inside a 120KB working budget.

Q2Your callpermissions

Who stops the verification server

The runtime tier needs a local HTTP server for the duration of the checks. The plan grants Bash(kill:*) and scopes its use by wording — the skill kills only the pid it recorded. The grant itself is broader than that.

Q3Your callrelease

Do the fixtures ship inside the released plugin

Three fixture pages at 48-60KB each. They are the regression suite, so they must live in the repository; whether an installed copy of chat-tools also carries them is a separate question. The plan takes no position — this card carries no recommendation, so Accept all skips it and the untouched count treats it as unanswered.

Q4Your callform

Bare fragment, or a doctype stripped at publish

D-18 made the shell a bare fragment so one file serves both disk and the Artifact tool. The cost is quirks mode from disk, which the shell avoids by construction — lowercase selectors, explicit table type, no percentage heights, no image in a table. The cheaper cure is a doctype on line 1 and one sed at publish time, at the price of a publish step that can be forgotten.

Q5Your callpermissions

Confirm the skill's tool set

Edit and Write are absent from the skill's allowed tools. Every write to a page goes through splice.py, and the agent never reads the shell or a page copy — which is what keeps the chrome out of context. The kickoff named no tool set, so this is a confirmation rather than a change.

The ten build steps

Each is its own DraftHorse heading with its own start and finish conditions. The error step stands alone as step 10.

  1. Open the build — decide kind, layout class and id slug, verify the slug is unused, decide new page versus revision.
  2. Load the page kind — read the kinds reference, then the one page template the kind maps to. Never a second page template. Read it for its exemplars and instruction comment only.
  3. Resolve provenance — run the git facts, derive repo, root, self, branch, commit, date and build stamp; PR from gh; issue from the task or null.
  4. Instantiate the shell — cp the shell, fill the three placeholder regions, set the layout class. Never read the shell or the copy.
  5. Splice the template — lift each part mechanically, once per page. Never retype a scoped style or a block script.
  6. Write the cards — one splice per card into its section. The agent types only the cards.
  7. Revise a published page (dormant) — open with the two show forms, splice only the changed cards, bump the revision.
  8. Verify the page — static tier, then runtime tier. Repair before hand-over; report a skipped tier with its reason.
  9. Hand the page over (success) — report the path, id, revision, card count and checks run.
  10. Handle a build problem (error) — missing marker, slug collision, unparseable meta, splice failure, no browser, or a shape no template covers. The last one hard-bails and raises an issue.
