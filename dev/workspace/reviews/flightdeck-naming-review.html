Takes

The six positions from the chat reply plus one on profiles. Each is an option set where the choice is genuinely yours; the rest are recommendations.

01Your callnaming

FlightDeck as the family name

Fits the library's naming register (DraftHorse, git-box, magic-reply, corpus-sweep). Distinct from artifact, which is overloaded three ways on this branch: the claude.ai Artifact tool, dev/workspace/artifacts/, and the artifact-suite skill name. That overload alone justifies a coined name.

Caution: deck collides with slide decks in casual chat. Define it once in the framework doc and the collision is harmless.

02Your callnaming

Two profiles under one family: deck and page

You have two kinds of thing, not one. Deck — a durable instrument like prompt-builder: opened daily, versioned, carries its own state (localStorage, File System Access), lives in extensions/. Page — a task artifact like a review or interview: generated once, disposable, lives in the workspace, carries a return prompt. Same shell, very different lifecycle.

Resist theming the sub-names (sortie, instrument, cockpit). Durable-documents rule: every coined term needs a home in the doc, and two coined terms is enough.

03Your calllocation

Landing rule: page kind decides the directory

Claude placing reviews in reviews/ and plans in plans/ is right. The dev-workspace directories already carry meaning, and archive, commit and history all work on them for free. A catch-all artifacts/ duplicates that meaning and hides the page's purpose.

Proposed table: review page → reviews/; interview, options and decision pages → plans/; demo, dashboard or anything with no natural home → flightdecks/, a rename of the experimental artifacts/ directory. This overrides the plan's single-directory landing rule (D-19, tech plan File layout).

04Integratelocation

Durable decks live in extensions/flightdecks/

Rename extensions/artifacts/. Each deck at extensions/flightdecks/<name>/<name>.html with its own README, symlinked into a plugin like every other asset. The skill's build material (shell, templates, blocks) stays inside the skill directory; it is not a deck.

Repo docs mirror DraftHorse: docs/flightdeck/ for conventions, profiles and delivery; skill at extensions/skills/flightdeck/; optional rule in extensions/rules/. Cheap now — the plan is not yet built.

05Integratedw

dev-workspace integration

dev-workspace is its own repo. The scaffold change (add flightdecks/ with a .keep) belongs there; the tree config picks it up automatically.

Worth a named tree (dev-workspace tree) listing decks and pages across the live workspace and every dev/branches/ archive — that is the high-level insight surface for pages.

Archives are the killer feature: task pages snapshot with their context. Argues strongly for pages living inside dev/workspace/ and never in scratch or tmp.

06Your calldelivery

Delivery: keep Artifact-tool compatibility

Three surfaces: disk (file://, disk-primary links per D-18), a published Artifact (stable URL, shareable), and browser MCP for verification. Compat cost is small — verify writes the wrapped copy — and it is the only way a durable deck becomes a true daily driver across machines and projects.

Convention: decks publish once with a stable URL recorded in the deck's README and redeploy to the same path; pages stay on disk and publish only on request. Cross-project deck access otherwise goes through ${CLAUDE_PLUGIN_ROOT} after plugin install. Settles PIVOT §8's first open decision.

07Integrateprofiles

Profiles as the documented axis

deck — persistent state, versioned with a plugin, no return prompt, own README. page / respond — respond surface plus return prompt, kind-to-directory landing, disposable. page / read-only — demo, dashboard, figure; no state.

Profile is what the skill dispatches on; the three templates hang under it.

75Your call

File form

  • Bare fragment: no doctype/html/head/body — open, PIVOT §8 builds against dropping it.
  • Four quirks-mode rules: lowercase class/id names; explicit font-size/line-height on td/th; no percentage heights; no image in a table.
  • Non-ASCII CSS content written as escapes (\2212, \00B7).
  • Version stamp on line 1, read by text.
  • Self-contained single file; only the Google Fonts link and a data-URI SVG favicon leave the file.

78Integrate

Theme and tokens

  • Three theme blocks always: light on bare :root; dark under the media query guarded by :not([data-theme="light"]); dark again under [data-theme="dark"].
  • 14 original tokens plus exactly seven diff tokens; nothing else is ever added.
  • Radius hardcoded: 2px controls, 3px cards — “no token, indirection over a constant”.
  • Two prose measures: 68ch on card prose and section intros; 62ch on standfirst, gloss, blockquote.
  • No template or block names a font family, a raw colour, or restates a shell selector.
  • Three-way theme control; System removes the attribute and the stored key.
  • :has() allowed (Chrome ≥105); only adds state the control already expresses; the one load-bearing use carries an @supports floor.

Source: plans/artifact-suite-implementation.md § Tokens, § Theme control; D-4

79Integrate

Marker regions and writing a page

  • Seven regions, each exactly once. PIVOT §7 set: @doc-title, @page-meta, @masthead, @content, @sidebar, @demo-style, @demo-script.
  • Placeholder regions are replaced whole; empty regions fill by rewriting the closing marker into content plus the same marker.
  • One writable attribute outside the markers: the class on .shell.
  • Each section carries <!-- @end-<sectionId> --> before its closing tag (Edit anchor).
  • A page is created by cp, never by writing chrome. Never read the shell; never read a page copy in full — bounded Read with offset/limit, ranges found with grep -n.
  • splice.py deleted (PIVOT §6); Edit and bounded Read replace it.
  • The shell carries everything reusable; nothing is spliced, lifted or pasted at build time (PIVOT §5).

87Integrate
