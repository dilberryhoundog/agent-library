Review

8 findings

Where it landed

De-hold retires — the framework contradicts it and two-thirds of the corpus already ignores it. Precedence and scoping are rejected: precedence blocks the backtrack it was meant to protect, and scoping exists only to unlock what precedence locks. The state they were chasing — a user withdrawing approval — is a claimed remainder at the support step, which the conventions already sanction. One rule out, nothing in, one vocabulary fix.

01Confirmed

De-hold is unearned, and the corpus already voted

In play defines a step as a span with an end — "from when its start condition activates, until its finished condition is met". A span that ends at the finished condition needs no negated copy of it in the start condition to stop. The Looping function and the mandatory checkable test say the same thing from two other directions.

Practice agrees. De-hold is mandatory and the corpus carries it on roughly a third of its steps:

de-hold-shaped start conditions / total steps drafthorse/SKILL.md 0 / 9 git-box/SKILL.md 5 / 7 classroom/SKILL.md 10 / 13 versioning/SKILL.md 5 / 10 agent-push/SKILL.md 0 / 3 git-robot.md 1 / 3 ≈31 across ≈84 steps — and nothing has looped

The failure it guards against is a state-machine failure. A state machine re-evaluates a predicate with no memory. An agent has the transcript, and does not re-gather requirements because "the skill has been invoked" still reads true.

02Rejected#45's remedy

Precedence and scoping fail a test the framework already wrote

conventions.md, first bullet, settles this without needing the argument:

Every addition pushing the spec toward code — mandatory machinery, guaranteed coverage, a rule per state — steals from that purpose… An addition that only makes the document more complete is bloat.

Precedence is a rule per state. Scoping is a clause per condition. Neither makes the executing agent do more, more consistently, for less.

Worse, they cancel each other. De-hold blocks re-entry through the start condition; precedence blocks it through the finished condition — the same lock on a different door. Scoping then exists to unlock it. Three rules, one imaginary problem.

03Walkedruntime navigability

The runtime walk: de-hold removal fixes the backtrack

Scenario — at +Deliver, the user rejects the step map. Eligibility against the de-hold-free conditions on drafthorse-step-anatomy:

Step Start condition Eligible
+Collect References Requirements are established yes
+Map the Steps Reference set approved, no unfilled gaps yes
+Set Invariants The step map is approved yes
+Draft the Skill Invariants are approved yes
+Review A complete draft exists yes

Every start condition is a durable state, so it is still true when the agent comes back to it. Re-entry into +Map the Steps is unobstructed, and the conceptual listing order says where to resume.

Both alternatives break this exact walk:

Under de-hold

+Draft the Skill read "Invariants are approved and no complete draft exists". After a map change a draft does exist — the step is barred. Re-mapped, and unable to redraft.

Under precedence

+Draft the Skill finished on "the draft is written to the destination" — met, so barred permanently, with no clause to re-read a way out of.

Caveat: this walk was made with the discussion in context. A true cold read needs a fresh session.

04Resolvedclaim the remainder

The support step already carries revoked approval

"Arggg we stuffed up, can we redo this?" is a state no working step claims, so +Handle a Problem catches it by construction. Its finished condition is "the user has decided how to continue" — and that decision is the state change.

The withdrawal then cascades through conditions that were already written:

  1. The step map is approved → false → +Set Invariants and everything reading forward from it go ineligible.
  2. Reference set approved, no unfilled gaps → still true → +Map the Steps is eligible.
  3. Map re-approved → +Set Invariants eligible again → the run re-grows forward, in order.

The dependency graph was already there: every start condition names the approval it depends on. Withdrawing one approval collapses exactly the right subtree and no other. That is the cascade #45 wanted to buy with a scoping rule, already paid for.

And the skill-specific handling has a sanctioned home — conventions.md, Claim the remainder: "can guide the agent on how to resolve the skill if no other step handles the recoverable state. The remainder needs to be actively described." An approval cascade is a recoverable state, actively described, in that step's engagement.

05Regression

The mechanism was stated, and left with a retired slot

Commit 4a87a56 removed +Handle a Problem's Suggested next actions. This went with it — the corpus's only statement of the backtrack:

- Resume the phase the user chose — revising an approved artifact un-approves it and everything downstream of it, so that phase's start condition holds again — or end the build.

The rule was carried by the slot #38 retires. It needs a home in the framework, not a rebuild as machinery.

06The whole gap

Vocabulary, not mechanism

Every description of the step says error, failure, unrecoverable, problem state. A withdrawn approval is none of those — nothing went wrong, the user changed their mind. Claim the remainder covers it in substance and excludes it in wording:

The error step can guide the agent on how to resolve the skill if no other step handles the recoverable state.

Recoverable state is broad enough. The surrounding prose is not — it reads as failure handling throughout, so a builder does not think to write an approval cascade there, and a runtime agent does not think to look. One worked example inside that disposition closes it.

Adocs/drafthorse/framework/steps.md

Widen Claim the remainder by example, not by rule

The disposition stands as written. It gains one worked case, so a withdrawn approval reads as claimable rather than as an error:

Now — the class catalogue

Half-applied state · Failed permissions · Insufficient references · Named recoverable failure. Four classes, all failures.

Proposed — one class added

Withdrawn approval — claim the remainder. The user rejects an approved artifact and asks to go back. Record the withdrawal; the steps depending on that approval go ineligible and the owning step is eligible again. A skill needing a specific cascade describes it here.

§ User gates loses its cascade sentence — "un-approves it and everything downstream of it, so the owning step's start condition holds again" — and keeps the plain fact: approval is state the user can withdraw. The downstream effect is what the existing conditions already do, not a rule.
