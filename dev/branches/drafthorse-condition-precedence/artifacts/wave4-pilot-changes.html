Rule these changes serve
  1. Start not met — the step does not run.
  2. Start met, finish not met — the step runs.
  3. Finish met — the step does not run.

Start conditions therefore stop carrying a negated copy of their own finish. Issue #45 holds the framework side; your spec work for it sits on drafthorse-condition-precedence.

Decisions taken, and what they cost

Rejected — scoping phrases on gate finished conditions

Four gates were to gain "approved against the established requirements", "against the approved reference set", and so on, so a revised upstream artifact would unstick everything below it. Dropped: the jam they defended against was an artefact of de-hold's process-negations, which no reading could invalidate. With every finish an artifact fact, an agent reading a stale approval handles it. Also the direction commit 6c92e14 set — lean on the model's reading, treat bloat toward code as the danger.

Residual risk, stated plainly: a cold agent resuming a long-abandoned build sees an approved map and a changed reference set with no conversation history. It must infer staleness from the artifacts alone. Judged acceptable; if it bites, the scoping phrases are the fix and they go on the finished conditions.

Rejected — an explicit abandoned-run exit

"The user has decided how to continue" already covers deciding to stop, and the spec-check no longer demands a stated exit — The run resolves is judged on the scenario walk. Applied to the template, then reverted. Applies equally to the pilot's error step.

Retired outright — the un-approval cascade

Considered as a global invariant, a Terms entry, a dormant step and a routing step across the session. None survived: once de-hold goes, the fact is emergent. Note this diverges from the parallel work on drafthorse-condition-precedence, which rehomes it into +Handle a Problem's engagement prose. One of the two gives way at the merge.
