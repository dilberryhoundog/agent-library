1 · Shape — one skill, prebuilt profiles

The skill holds the pattern. Each corpus gets a profile built and reviewed here, in advance. At sweep time the main loop selects a profile — it never authors one.

extensions/skills/corpus-sweep/
├── SKILL.md                       eight steps, a DraftHorse document
├── references/
│   ├── writing-briefs.md          what makes a brief tight enough to downtier
│   ├── model-tiering.md           the policy the last sweep paid to learn
│   └── failure-recovery.md        worktree discard, resume, classifier stalls
└── profiles/
    ├── drafthorse/
    │   ├── manifest.yml           assignments, tiers, file ownership
    │   ├── migrate.js             worktree per agent, destructive
    │   ├── audit.js               read-only, spec-check authority
    │   ├── brief-common.md        spine + slots for this sweep's payload
    │   ├── brief-assignment.md    per-target template
    │   └── brief-audit.md         near-verbatim from the executed sweep
    └── dev-workspace/
        ├── manifest.yml           one assignment per repo
        ├── migrate.js             no worktrees — repos are separate trees
        ├── audit.js               authority is `dev-workspace init --check`
        └── brief-*.md
Why profiles beat one parameterised script. The two corpora differ where it matters. DraftHorse edits documents inside one tree, isolates agents with worktrees, integrates locally, and ships two PRs. dev-workspace rewrites a payload across separate repositories, needs no worktrees because each repo is already its own tree, and ships a PR per repo. A single script serving both would branch on topology through setup, git handling, and audit invocation — two programs wearing one costume. Separate profiles stay readable, and each is reviewed once here rather than generated under pressure at sweep time.

2 · The run

Seven stages. The only network is at the end.

Stage detailsettled
  • 1 Select. Main loop reads the spec change, picks the profile, fills its manifest — assignments, file ownership, tier per assignment — and writes briefs from the profile's templates. Strong model; this is where all downstream judgment is pre-decided.
  • 2 Approve. You read briefs and tiers before a single agent runs. Nothing is spawned until you say so.
  • 3 Migrate. One agent per assignment, each in its own worktree, each committing its own work there. Agents never push and never touch gh. A dead agent's partial work dies with its worktree — no reset procedure, no file-ownership bookkeeping.
  • 4 Integrate. Main loop cherry-picks each assignment's commit onto the sweep branch, giving a linear history of one commit per site. After each pick, the commit's changed-file list must equal that assignment's manifest file list — any extra path means the agent wandered outside its brief, and that routes to the error step. Then the cheap verification pass re-reads the integrated tree against the briefs.
  • 5 Audit. Read-only agents against the integrated sweep branch, no worktrees, authority set by the profile. Main loop triages findings into clear-cut repairs and decision cards.
  • 6 Review. A page like this one. You answer, copy, paste back.
  • 7 Push. Main loop pushes once and opens two PRs. Releases stay out of scope — the skill hands off to /dev-tools:versioning.

3 · Git model

Every commit is a self-contained, reviewable diff on GitHub. That is what makes a single PR per provenance sufficient — the per-site granularity lives in the commits, not in the PR count.

4 · What reversed, and why

Four calls from the first round did not survive contact with the second. Recording them because the reasons matter more than the verdicts.

Worktree per migration agentreversed
Originally rejected on the grounds that disjoint file sets make conflict impossible. True, and beside the point — conflict was never the real risk. Unobservable partial failure was: five dead agents last run left half-applied edits in a shared tree, and recovery meant guessing which files each had touched. A worktree makes that vanish with the worktree. Setup runs a few hundred milliseconds against agents that work for minutes.
Prebuilt per-corpus profiles, not one parameterised pairreversed
A generic script serving unknown future corpora accretes conditionals for cases nobody has. The durable asset is the pattern — fan-out shape, schemas, tiering, provenance — and that belongs in the skill and its references. Profiles are cheap to build and cheap to read.
Manifest is per-corpus, not a universal schemaloosened
With a bespoke script reading it, the manifest needs no scope: or audit.mode: seams. Each profile shapes its own. The four audit modes survive as authoring guidance in a reference, not as an enum.
Failure recovery simplifies to discard-and-rerunsuperseded
The manifest-driven reset was solving a problem worktrees remove. The manifest's file list keeps a better job: asserting after integration that a commit touched exactly the files its assignment owns.
Carried unchanged from round 1settled
  • Skill is a DraftHorse document, drafted by invoking the DraftHorse skill.
  • Briefs authored in the main loop from profile templates, approved by you before any agent runs.
  • Two workflows per profile — destructive and read-only kept apart as a visible safety boundary.
  • The verification pass, promoted from the accidental second pass the last sweep got for free.
  • Tiers high / standard / mechanical resolving to explicit models. high is opus, never inherit — a Fable-authored sweep would otherwise reintroduce the blowout.
  • Eight-step map; integration folds into +Migrate rather than earning its own step.
  • Working set under dev/workspace/tasks/<sweep>/; review pages in dev/workspace/reviews/.
  • The pilot convention, agent self-verification, audit independence, the sanctioned-shapes list, the cold-read experiment, structured returns.

5 · Still open

N1 · Skill nameneeds a call

corpus-sweep reads right for a tool with profiles and matches the vocabulary already in use. It is also short enough to invoke. Alternatives worth a moment: corpus-migrate names the destructive half only; sweep is briefer but collides with nothing and means nothing.

N2 · Which profiles ship in this buildneeds a call

DraftHorse can be built from evidence — the executed sweep gives real briefs, a real manifest, and two working scripts. dev-workspace would be built from a sketch: no sweep has run, so its brief templates and its init --check audit path are guesses until one does. Building both now risks shipping a profile that turns out wrong on first contact.

N3 · Does the skill create its branch via dev-workspaceneeds a call

A sweep needs a branch and a working directory. dev-workspace new <sweep-name> already produces both, with the workspace folders the manifest and briefs want to live in, and the archive behaviour that keeps a finished sweep readable later. The cost is a hard dependency: the skill stops working in any repo without dev-workspace installed — which matters exactly for the dev-workspace profile, whose targets are repos that may not have it yet.

N4 · Fate of the two scripts in .claude/workflows/needs a call

They are the source material for the DraftHorse profile and they carry a live hazard: hardcoded targets, brief paths that exist only in an archive, and two audit rows that silently inherit the session model on a fresh run. Once the profile exists they are strictly worse copies. Deleting them is clean; keeping them means someone eventually runs the expensive fossil by accident.

N5 · Build orderneeds a call

Proposed: references first, since the tiering and failure-recovery knowledge is the part that would be lost if this stalls; then the DraftHorse profile's workflows and manifest, which can be tested against the already-migrated corpus without editing anything; then brief templates; then the SKILL.md last, via the DraftHorse skill, once its steps describe something that exists. The alternative is SKILL.md first as a spine to hang the rest on.
