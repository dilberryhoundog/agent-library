The premise. The two workflow scripts were never the whole tool — they are phases 5 and 6 of an eight-phase process. Everything expensive and everything judgment-bearing happened in the main loop around them. So the tool is a skill; the workflows survive inside it as separate, unchanged-in-spirit assets. What follows proposes the skill's shape and asks you to settle twelve calls.

1 · The shape at a glance

The executed sweep ran eight phases across three actors. Reading the lanes tells you where cost and judgment actually sat: the two workflow bars are the only places agents fanned out, and they sit between four main-loop phases that did the thinking.

Phases 4 and 5 are the existing scripts. Phases 1–3 and 6–8 are main-loop work the skill has to encode, because that is where the judgment and the cost concentrated.

2 · Where it lives

Two homes, and they do different jobs. The skill is a durable asset in the library, versioned and shipped in a plugin. The sweep working set — manifest, briefs, results, review page — is throwaway per-sweep state, and dev-workspace already guarantees a place for it on any branch.

Why agent-tools. The DraftHorse skill and the saddler agent already ship there. A sweep tool that migrates DraftHorse documents belongs beside the framework it serves, and it inherits the same release unit — one agent-tools version covers a spec change and the sweep that propagates it.

D1 · The skill is itself a DraftHorse documentproposed

A skill that migrates DraftHorse documents, written as a DraftHorse document: steps with start and finished conditions, an error step, a success exit. It dogfoods the framework and it makes the skill a corpus member — so the next sweep migrates the sweep tool too, which is a genuine test of the spec. Cost: sweep phases are long-running and interruptible, and DraftHorse conditions have to carry resume semantics honestly rather than pretending the run is atomic.

D2 · Home and working set as drawn aboveproposed

Skill in extensions/skills/drafthorse-corpus-sweep/, symlinked into agent-tools. Per-sweep state under dev/workspace/tasks/<sweep-name>/, which the last run already used and which survives any branch. Review page to dev/workspace/artifacts/. The alternative is a standalone plugin, which buys independent versioning at the cost of splitting the framework from its migration tool.

Eight working steps plus the two exits. Solid arrows are the happy path; each step's start conditions are what actually route, so the diagram is a reading aid, not the contract. The two shaded steps are the ones that invoke workflows.

The looping declaration on +Migrate is what makes interruption survivable: an assignment with no recorded result is the per-item discriminator, which is the sanctioned loop shape under the current spec.

Eight working steps, two exits, no handover documents. 4 · The manifest — one interface, two consumers

This is the load-bearing idea. Both workflow scripts currently carry hardcoded arrays of targets and brief filenames, which is the single reason they are one-off. Replace both arrays with one file the skill writes and both scripts read, and the scripts never need editing again.

One file drives fan-out, model tiering, and failure recovery. Nothing in either script mentions a document name.

D4 · Manifest as the sole interfaceproposed

The skill writes it in +Inventory; both workflows read it and nothing else sweep-specific; the reset procedure reads files to know exactly what a dead agent touched. Format shown is YAML for hand-editability — you will be reading and adjusting this file, since it is where you set tiers. JSON would save the workflows a parser, at the cost of being unpleasant to edit.

5 · The briefs — spine and payload

The last run's brief-common.md is 66 lines and splits about half and half. The half that generalises is a spine; the half that does not is this sweep's payload. The template makes that split explicit with named slots.

brief-common.md — what stays and what becomes a slot

## Read first, in order
− 1. docs/drafthorse/framework/steps.md — step anatomy, the function catalogue…
− 2. …references/step-functions.md — the six shapes and their fixed strings.
− 3. …references/condition-writing.md — condition rules.
− 4. …drafthorse/SKILL.md — the migrated pilot.
+ {{SPEC_DOCS}} — from the manifest, numbered, in order.
+ Last: {{PILOT}} — the migrated pilot. The worked reference for every shape below.
 
Then read your target file(s) whole. Edit with the Edit tool, site by site.
Never edit via script or sed. Never edit any file outside your assignment.
Framework docs are frozen — where your target disagrees, the target changes;
where the migration seems to demand a framework change, flag it instead.
 
## Fixed texts — byte-exact
− Universal preamble. Replaces the old quote-block preamble…
− Steps are universal and standalone. Marked ## +<Step Name>. Work, instructions…
− Function declaration strings — **Error step** — Handles recovery and bails. …
+ {{FIXED_TEXTS}} — every string this sweep requires byte-exact, with the
+ text it replaces. Empty when the sweep introduces no fixed strings.
 
## Checklist, applied per step in one pass
− A. Preamble … L. Out-of-scope defects (twelve lettered items, sweep-specific)
+ {{CHECKLIST}} — lettered items, one per class of change this sweep makes.
+ The last item is always: out-of-scope defects go to flags, never fixed.
 
− ## De-hold judgment (issue #45's three classes)
+ {{JUDGMENT}} — where a rule changed and each site needs a call, name the
+ classes and say what to do with each. Omitted when the sweep is mechanical.
 
## Register — match the target's prose. Fixed strings byte-exact.
## Output — return ONLY the structured object the schema demands.

Unchanged lines are the spine: read-order with the pilot last, Edit-tool-only, frozen-framework precedence, flag-never-fix, register, output contract. Four slots carry everything sweep-specific.

Why this matters more than it looks. Brief tightness is what bought the model downtier. The last run's own accounting: roughly 8 of 13 assignments were Sonnet-safe because the briefs pre-decided the judgment. A loose brief forces a strong model on every assignment. That makes brief authoring the one phase where spending a strong model pays for itself several times over — and it argues against generating briefs cheaply.

D5 · Briefs stay main-loop authoredproposed

Three ways to get briefs. Main-loop authored — as last time: the strong model reads the spec change and writes all N briefs, you approve them, downstream agents run cheap. Agent-generated — one agent per target writes its own brief then migrates; cheapest to build, but the brief and the migration share a head, so nothing pre-decides the judgment and the tier cannot drop. Hybrid — a cheap agent drafts each brief from the manifest and the spec diff, main loop tightens and you approve; saves main-loop tokens, adds a review burden.

Those two null, null rows are the sharpest lesson in the whole archive. They exist only so a mid-run resume replayed them from cache. On a fresh run they silently take the most expensive tier available — the exact failure the pivot was supposed to fix, preserved in the code that fixed it.

D6 · Two workflow files, invoked by the skillproposed

Keep migrate.js and audit.js as separate assets under the skill. They run at different phases, have different schemas, and one is destructive while the other is read-only — which is a real safety boundary worth keeping visible. The alternative is one script with a mode flag, which halves the shared boilerplate.

D7 · Promote the accidental verification passproposed

When the last run was interrupted, replacement agents found their predecessors' edits already in place and byte-verified every hunk against the brief instead of re-editing. The interruption bought a free second pass, and it was the assistant's own note that this was a silver lining. Proposal: make it deliberate — a cheap verify stage inside the migrate pipeline, one agent per assignment at haiku/low, that re-reads the edited files against the brief and reports mismatches without touching anything. Cost is small; it catches the class of error the audit is not looking for, because the audit judges the document as shipped and never sees the brief.

7 · Model tiers — the policy the last run paid to learn

The run began with every agent on the session model at maximum effort, and ended after you said it was about to blow a week of credits. The policy it converged on is recorded in the transcript and nowhere in the code. Encoding it is most of the value of doing this at all.

Cheaper to migrate on Sonnet and audit strong than the reverse. Single-file audits sit at sonnet/medium; only multi-document sets earn the top tier.

D8 · Tier defaults baked into the workflowsproposed

Three named tiers in the manifest — high, standard, mechanical — mapping to model and effort inside the script, with standard as the default so an unmarked assignment is never accidentally expensive. Audits tier off audit_as rather than off the migration tier, because a document can be easy to migrate and hard to judge as a set. The counter-position: leave every tier explicit in the manifest and let the skill propose values you approve at brief time, so nothing is ever implicit.

8 · Failure recovery

Five of thirteen migration agents died mid-run — three connection drops, two session limits — and eight of twelve audit agents died on a limit. Recovery worked, but it was hand-reconstructed. The manifest makes it mechanical.

D9 · Manifest-driven reset before every resumeproposed

A rule in the skill's +Migrate step: before resuming, reset the files of every assignment with no recorded result. Because the manifest owns the file list, this is one command built from data, not a reconstruction. It also makes the loop honest — an assignment is unfinished exactly when its result is missing, which is the per-item discriminator the Looping declaration needs.

D10 · No worktree isolationproposed

The Workflow tool can give each agent its own git worktree. Proposal: do not. Migration agents edit disjoint file sets by construction — the manifest guarantees it — so there is nothing to conflict over, and worktrees add setup cost per agent plus a merge-back step that becomes its own failure surface. The manifest-driven reset covers the case worktrees would have covered. The counter-argument is that a misbehaving agent editing outside its assignment would be contained; last run, none did.

9 · The review loop

The page you are reading is the mechanism, and it worked: 18 decision cards went out, verdicts came back as one markdown block, and the main loop applied them in a batch. Worth keeping exactly as it is, with one open question about where the file lands.

D11 · Review page as a local workspace fileproposed

Written to dev/workspace/artifacts/<sweep>-review.html from a template asset, as last run and as this page. It stays with the branch, archives with the workspace, and needs no network. The alternative is publishing it as an Artifact — shareable link, comment threads, no local file to open — at the cost of leaving the workspace's own history.

10 · Scope of the tool

Everything above is written for DraftHorse. Almost none of the machinery is DraftHorse-specific: a manifest of assignments, briefs from a template, a fan-out that edits, a read-only fan-out that audits against a checker document, and a decision page. That describes any spec-driven bulk document migration.

The DraftHorse-specific parts are exactly four: the pilot-document convention, the spec-docs read list, the audit's authority being drafthorse-spec-check.md, and the sanctioned-shapes list that suppresses known false findings. All four are already manifest fields or brief slots in the proposal above — which means the generic version is nearly free, and the question is only whether to name it generically now or later.

D12 · Name it for DraftHorse, keep the seams genericproposed

Ship as drafthorse-corpus-sweep with DraftHorse defaults baked into the templates, but keep every spec-specific value in the manifest rather than in the scripts. If a second corpus ever needs sweeping, the rename is cheap and the internals already fit. Naming it generically today means writing documentation for a use case that does not exist, which is the more expensive mistake.

Round 2 · raised after the first verdicts

Round 1 is settled — D1–D11 as answered, recorded in dev/workspace/context/sweep-tool-decisions.md. Two adjustments landed with them: the review page moves to dev/workspace/reviews/, and tier high now resolves to an explicit opus rather than inheriting the session model. That second one is the better call — a sweep authored in a Fable session would otherwise silently reintroduce the exact cost blowout the tiering exists to prevent. No tier is left unset anywhere.

D12 reopens. The case for a universal tool was that a second corpus does not exist. dev-workspace makes it exist. Four questions follow.

11 · Two topologies, one process

dev-workspace is a genuinely different shape from DraftHorse, and the difference is worth seeing before deciding whether one tool covers both. DraftHorse sweeps documents inside one repository. dev-workspace sweeps repositories — each holding its own copy of config, rules and CLAUDE.md, each drifting from the current skill version.

Everything else is shared: manifest, brief template, editing fan-out, structured change records, tiering, failure reset, triage, review page.

The apparent blocker — dev-workspace cannot audit itself — dissolves on inspection. It has a conformance check; the check is a command, not a document. So the audit phase does not need removing for the second corpus, it needs generalising from "read the checker and execute it" to "establish conformance by whatever authority this corpus has".

# manifest — the two new seams
scope: documents          # documents | repos
audit:
  mode: spec-check        # spec-check | command | canonical-diff | none
  authority: docs/drafthorse/drafthorse-spec-check.md

# the dev-workspace profile of the same file
scope: repos
audit:
  mode: command
  authority: dev-workspace init --check
canonical:    # stands in for 'pilot'

E1 · Build it as a universal corpus-sweep skill with profilesreopens D12

Ship as corpus-sweep, with DraftHorse as the first profile and dev-workspace as the second when you need it. The argument that killed this in D12 was that no second corpus existed; it does now, and renaming a released plugin skill later is the expensive move — symlink, manifest, tag, changelog, and every install path. Build the DraftHorse path fully; leave the repos path named and unimplemented until a real dev-workspace sweep calls for it. The counter-position stands if you would rather two focused skills that share nothing but a family resemblance.

E2 · Audit becomes a mode, not a fixed procedureproposed

Four modes. spec-check — read a checker document and execute it, exactly as DraftHorse does now. command — run a conformance command per assignment and report its output as findings, which is dev-workspace's init --check. canonical-diff — diff each target against a canonical source and report drift, for corpora with neither checker nor command. none — skip the phase; the verification pass from D7 is then the only safety net, and the skill should say so rather than pretend the sweep was audited.

12 · Git — who commits, and when

Your instinct is right and the constraint is sharper than it looks. Under D10 the migration agents share one working tree. Thirteen agents cannot each cut a branch in one tree — the first checkout would drag every other agent's in-flight edits with it. So in the document topology, agents must never run git at all. What makes per-assignment commits possible anyway is the same property that made worktrees unnecessary: the manifest already declares exactly which files each assignment owns.

E3 · Agents never touch git; the main loop commits per assignmentproposed

Immediately after the migrate workflow returns — and after the reset and the D7 verification pass, so a half-migrated file never gets committed — the main loop stages each assignment's manifest file list and commits it on its own. Thirteen assignments, thirteen reviewable commits, each traceable to its brief. The alternative you floated, PR-per-agent-run, is not available in the document topology for the concurrency reason above; it becomes available and natural in the repos topology, where every assignment is its own tree.

E4 · Two sequential PRs, split by provenanceproposed

This is the direct answer to the unscoped changes you spotted. PR 1 — briefed work: the per-assignment migration commits plus any separately briefed one-off like the 6b harvest. Everything in it was planned and approved before an agent ran. PR 2 — found work: clear-cut repairs from the audit, then the verdicts you return from the review page. Nothing in it was scoped in advance. PR 2 depends on PR 1, so they stack rather than run parallel, and the set-level audit needs the whole migrated corpus in place before it can judge anything — which fixes the ordering anyway.

Carried forward without a decision

Techniques kept as-is from the executed sweepno change proposed
  • The pilot as worked reference. Every brief pointed at one already-migrated document as the exemplar for every shape, read last. Cheaper and more reliable than describing target shapes in prose. Becomes the pilot manifest field.
  • Agent self-verification. Each migration agent grepped its own targets for the retired strings its brief named and returned the results inside its structured record. Kept verbatim.
  • Audit independence. Auditors run read-only, from a cold read, against the checker document, and never see the migration briefs — so findings judge the document as shipped rather than as intended.
  • Sanctioned-shapes list. A short list of known false positives handed to every auditor kept findings signal-dense. Becomes a brief slot.
  • The cold-read experiment. One contested design question was settled by handing the disputed step to a fresh cheap agent and watching whether it got confused. Worth naming in the skill as an available move during triage.
  • Structured returns, not prose. Both workflows force a schema and tell agents their output is data for an orchestrator. Kept.
Known hazards recorded, no fix proposedfor awareness
  • The scriptPath form of workflow resume was refused by the safety classifier; the identical script passed inline with the same run id worked. Recorded in the failure-recovery reference.
  • One migration agent's work returned with the reviewing classifier unreachable. Its full diff was read by hand before the edits were trusted. The skill should say this out loud rather than leave it to chance.
  • Session limits hit both workflows. Nothing prevents this; the manifest-driven resume makes it cheap rather than rare.
