L96 § Condition Checks · Start conditions delete

1 · The De-hold check

Mirror of the bullet deleted from condition-writing.md. Left standing, it fails every document the sweep is about to correct.

- **State terms, never step terms** — "a report has arrived", not "after the previous step"…
- - **De-hold** — the condition must stop holding once the step's work is done, or the step re-admits itself forever. Even a first step needs its closing clause ("…and requirements are not yet established").
- **Negative space claimed** — across all steps the start conditions cover every state the document can be in…
L107 § Condition Checks · Finished conditions delete

2 · Approval is revocable state

The cascade paragraph deleted from steps.md § User gates, restated as a check — and its second clause actively demands the de-hold shape ("X approved and Y not approved"). Both halves go with the rule.

- **Gates are compound** — a gate's finished conditions state the artifact's own completion criteria alongside the user's approval…
- - **Approval is revocable state** — revising an approved artifact un-approves it and everything downstream, so the owning step's start condition holds again; gate-shaped start conditions ("X approved and Y not approved") depend on this and must not fight it.
- **Every outcome the step can end on** — a step whose work can end in failure, refusal, or a no-op states those outcomes…

L98 § Condition Checks · Start conditions optional

4 · Loops: name the terminator

Matches the wording now in condition-writing.md. With de-hold gone, what ends a loop is worth stating where the loop check lives.

- - **Loops are re-holding conditions** — a per-item step's condition simply holds again for the next item; no loop syntax exists. A loop expressed any other way is a finding.
+ - **Loops are re-holding conditions** — a per-item step's condition simply holds again for the next item, and the step's finished condition is what ends the loop; no loop syntax exists. A loop expressed any other way is a finding.
L131 § Step Function Checks optional

5 · "Something ends the loop" now has a name

The check already asks the right question; the answer used to be either the start condition ceasing to hold or a separate exit. Only one answer is left.

- - **Looping step** — the start condition re-holds, and something ends the loop.
+ - **Looping step** — the start condition re-holds, and the step's finished condition ends the loop.
L129 § Step Function Checks · Error step your call

6 · Should the checker know about the new class?

#45 added User approval problem to the disposition catalogue in steps.md. The checker condenses that catalogue into one line, and currently names three concerns. Adding a fourth makes a gated document answer for where a withdrawn approval lands.

- - **Error step** — remaining errors claimed after each step handles internally, destructive errors handled, half-applied states accounted for.
+ - **Error step** — remaining errors claimed after each step handles internally, destructive errors handled, half-applied states accounted for, and in a document with gates, a withdrawn approval dispositioned.

Argument against: the class catalogue is open, the checker names concerns rather than enumerating classes, and a document without gates would be answering a question that does not apply to it. Argument for: gates are near-universal in this corpus, and the disposition is exactly what went missing when the slot was retired.
