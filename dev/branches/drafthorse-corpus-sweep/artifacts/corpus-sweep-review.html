D1 · git-box gains +Concludeapplied

Load-bearing slot repair (Gap 1). git-box had no success exit: on a plain full success no start condition held and nothing ended the run — the deleted slot was the only exit. A new success step now claims the recorded full-success outcome; +Save a Workflow and +Help already ended their own branches.

+ ## +Conclude
+ End the run on a plain success and hand the conversation back.
+ **Success step** — Resolves the run's done state and exits.
+ Start: the report has been presented · the run's outcome is recorded as a full success
+ Finished: the user has the conversation back · the skill is complete

Alternative considered: an OR'd terminating finished block on +Present Report — rejected as giving one step two functions (working + success exit).

D2 · agent-switch +Stash no-op ends the runapplied

The behaviour question the slot audit flagged. Decided: a clean-tree stash no-op ends the run, reported (Option A — preserves shipped slot behaviour). Reason: continuing into an unstashed switch would also arm a chained pop to restore some unrelated pre-existing stash entry onto the new branch. Encoded in conditions: +Read Procedure's guard and +Result's claim both name the no-op; +Result's invariant now admits the no-op note.

Auditor dissent, on record: the Sonnet audit read this as the scenario-walk break — a chained SWITCH(stash, switch, pop) on a tree that happens to be clean no-ops the whole procedure instead of switching. Option B (no-op continues, pop guarded separately) would serve that intent but changes shipped behaviour. Your call stands either way.

Gap 2 rehome. The slot said "Release the chosen units one at a time, in the order chosen." The plan suggested a +Range step invariant — but +Range finishes before the release loop begins, and a step invariant lapses with its step. Landed global instead:

+ **ALWAYS** release the chosen units one at a time, in the order the user chose.
